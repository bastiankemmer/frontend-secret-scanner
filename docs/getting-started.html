frontend-secret-scanner

Check the text a person is typing for secrets, in the browser, before it is sent to your backend or to a model provider.

1. Install

npm install frontend-secret-scanner

It is plain JavaScript with type declarations, has no dependencies and uses no Node APIs, so it runs in the browser. The bundle is 4,574 bytes minified and gzipped. The published package is ESM only, with no require export.

The library only checks strings. It draws no UI, never changes your page, and sends nothing anywhere. Your app decides what to show and whether to send.

2. Your first check

Initialize a detector once. With no config you get the default checklist, strict mode, and detailed results. 

import { initializeSecretDetector } from "frontend-secret-scanner";

const detector = initializeSecretDetector();

const result = detector.check("Hey, can you debug my deploy?");
result.pass;      // true
result.allowSend; // true

The sentence is split on whitespace into tokens, and each token is tested against the rules. A token that matches a rule is a secret.

3. Reading the result

check(text) returns a result. It never throws on a secret. attach (below) gives you the same result in its callback.

Field Meaning
pass true when no token is a secret.
allowSend What your app should do. false in strict mode when a secret was found, otherwise true.
report "detail" or "boolean", from your config.
error Only with report: "detail" and a secret. A message and the matches.

A secret found with detailed results:

{
  pass: false,
  allowSend: false,
  report: "detail",
  error: {
    message: "Don't send secrets. This looks like: OpenAI API key.",
    matches: [
      { text: "sk-proj-...", start: 47, end: 95, rule: "openai", label: "OpenAI API key" }
    ]
  }
}

start and end are positions in the text you passed in, so you can highlight the secret. The message names the kind of key and does not repeat it. The matches do carry the token text, so do not log them.

Write the message your own way with the message option. {labels} is replaced by the kinds of key found, and a message without it is used as it is: 

const detector = initializeSecretDetector({
  message: "Remove the {labels} before you send this.",
});
// "Remove the OpenAI API key before you send this."

The default is Don't send secrets. This looks like: {labels}. The message is plain text, so it works in the config the config page builds. With a boolean report there is no error, so no message.

4. Wire it to an input

Pass your input, textarea, or contenteditable element to attach. It listens, checks the text, and gives you the result. 

const detector = initializeSecretDetector({ when: "onLiveChange" });

const stop = detector.attach(textarea, (result) => {
  warning.hidden = result.pass;
  if (!result.pass) {
    warning.textContent =
      result.report === "detail" ? result.error.message : "Don't send secrets.";
  }
  sendButton.disabled = !result.allowSend;
});

// stop() removes the listeners.
  • When it checks. when: "onLiveChange" listens to input, including paste and autofill. when: "onChange" listens to change. A contenteditable element does not fire change, so that mode listens to focusout. A send control that keeps focus (mousedown and preventDefault) never blurs the field, so use onLiveChange there. Enter is checked in both modes.
  • Enter in strict mode. If the text holds a secret, the Enter key event is stopped before handlers on the field see it. Your send-on-Enter handler does not run and a form does not submit. The guard is a capture listener on window, and it only acts when composedPath() includes the field. Listeners on the field run after it. A capture listener already on window before attach still runs first. Enter is blocked while isComposing or keyCode 229 only when the text fails the check; a clean field still commits. Shift+Enter is not blocked.
  • The Send button. A click on your own button is not stopped, because the library never sees it. Disable the button from the callback, as above.
  • Other elements. attach throws for anything that is not a text input, a textarea, or a contenteditable element.

You can also skip attach and wire it yourself: detector.check(text) checks a string. The warning, the colors, and the disabled button are always yours.

5. Strict mode

Strict is on by default. When a token is a secret, allowSend is false. Your app should refuse to send.

Turn strict off with strict: false to warn only. The secret is still reported, but allowSend stays true. 

initializeSecretDetector({ strict: false });

6. Boolean report

If you do not want the found token in the result at all, ask for a boolean report. You get { pass, allowSend, report }, and no error. 

const detector = initializeSecretDetector({ report: "boolean" });

detector.check(text);
// { pass: false, allowSend: false, report: "boolean" }

7. What it detects

The default rules:

  • AI providers: Anthropic, OpenAI, OpenRouter, Groq, xAI, Perplexity, Hugging Face, Replicate, Google API key and OAuth secret
  • Cloud and hosting: AWS, DigitalOcean, Fly.io, Heroku, Supabase, Databricks, Doppler, Grafana, age
  • Source and packages: GitHub (classic and fine-grained), GitLab, npm, PyPI, Postman, Linear, Atlassian, Shopify
  • Messaging and payments: Slack, Stripe live, Stripe webhook, SendGrid, Twilio, Square, Telegram bot, Discord bot, JSON Web Token
  • Private keys: PEM blocks (PRIVATE KEY, RSA, EC, DSA, OPENSSH, ENCRYPTED, PGP), also pasted on one line or inside JSON. Header lines such as Proc-Type and Version are allowed, and a line may start with >, #, | or *. A long ordinary word after the header is not a key.
  • Passwords in a URL: database connection strings and https://user:password@host
  • Keys that need a keyword: Mailgun, Heroku, HubSpot, Cloudflare, Discord, Netlify, Sentry, Bitbucket, Codecov, Okta, LaunchDarkly, Telegram, AWS secret access key

A key pasted as NAME=value, JSON ("apiKey":"...") or a URL query (?token=...) is found too, and the result points at the value. The same split works after =, :, quotes, a comma or &. Smart quotes, markdown *, and pipes are trimmed from the edges, as is a leading /, # or @. Zero-width format characters inside a key are flagged.

8. Keys with no prefix

Some keys look like any 32 hex characters. To avoid flagging every hash, these rules also need a keyword, such as the provider name, within 8 tokens of the key.

9. The config page

The repo has a page where you type sentences and configure the detector. Clone the repo and run: 

git clone https://github.com/bastiankemmer/frontend-secret-scanner.git
cd frontend-secret-scanner
npm install
npm run demo

Vite prints a local URL. The page has four parts:

  • Config: when, strict, and the result shape.
  • Checklist: turn any default rule off, or remove one you added.
  • Sentence: type text, press Check, and see each token. Send tries the send and is refused when strict says so.
  • Build: the config object for initializeSecretDetector, with Copy and Download.

10. Teach it a new key

A provider you use is missing? Show the page a real token and it builds the rule. Use a made-up key or one that has been revoked, not a live one.

Step 1. Type a sentence with the key

No token is marked, so the key is unknown.

Step 2. Click the token

The page guesses the shape: the prefix, the kind of characters, and the length. Correct the guess if it is off, then give the key a name.

  • A key with a stable start needs a prefix.
  • A key without one needs a keyword that appears near it, such as the provider name.

Step 3. Add shape

The key is detected right away, and the new rule sits at the top of the checklist.

Step 4. Copy the config

In the Build section, press Copy config and pass the object to initializeSecretDetector in your app. 

import { initializeSecretDetector } from "frontend-secret-scanner";

const detector = initializeSecretDetector(/* paste the config here */);

The config page learns a shape from the selected token. Click a token and the form fills in the prefix, body, and minimum length.

11. Custom rules

rules replaces the checklist. Leave it out for the default shapes. To add to the defaults, spread them in: 

import { initializeSecretDetector, secretRules } from "frontend-secret-scanner";

const detector = initializeSecretDetector({
  rules: [
    ...secretRules,
    { rule: "acme", label: "Acme key", keywords: ["acme"], source: "[a-f0-9]{32}" },
  ],
});
Field Meaning
rule A short id. The first rule that matches a token wins, so put specific shapes above broad ones.
label What the message calls it.
source A regular expression for one whole token. Write it without ^, $ or \b.
keywords Optional. The rule only matches with one of these words, in any case, within 8 tokens.
scope Optional. "text" searches the whole input, for secrets that span several tokens, like private keys.

A bad config throws when you initialize, for example an unknown when or a pattern that is not a valid regular expression, so you find out at startup.

12. Limits

  • It finds known shapes. A password or a custom key with no known prefix is not found, because guessing from randomness flags ordinary words too. Teach the shape instead (step 10).
  • A secret glued to a word with no delimiter is not reported.
  • A key split by a newline is not reported.
  • https://user:pa/ss@host is not reported: a slash inside an https password. A database URL may still contain /.
  • It runs on the client, so it helps people and honest apps. It does not replace a server-side check on what you store or forward.

13. Speed

With the default rules on an Apple M4: a 12-word sentence takes about 0.02 ms, a 100-word message 0.12 ms, and 1,000 words about 1.1 ms. Ordinary text grows roughly with its length, so checking on every keystroke is fine for chat-sized input. Run it yourself with npm run benchmark.
